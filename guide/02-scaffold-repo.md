# 02 — Scaffold the repo

**Goal:** the repo has the files every project needs before any app code
exists — ignore rules, line-ending rules, editor settings, and a working
Husky pre-commit hook. You make your first commit and push it.

---

## Step 1 — Open the repo and a terminal

1. In VS Code: **File → Open Folder…** and choose your repo folder —
   the copy you created with **Use this template** and cloned (see the
   README).
2. Open the terminal: `` Ctrl+` ``.
3. Check you're in the right place:

```bash
git status
```

✅ You should see `On branch main` (or `master`) and a list of
untracked files like `README.md`, `guide/`, and `.vscode/`.

> **Terminology:** the folder the terminal is "in" is the
> **working directory**. Every command in this guide says which folder
> to be in. Unless told otherwise, you're at the **repo root** — the
> top-level folder of your repo.

---

## Step 2 — `.gitignore`

**Connect the dots.** Some files should never be committed:

- things you can regenerate (`node_modules`, `.venv`, coverage reports)
- things specific to your machine (the database file, caches)
- secrets (`.env` files)

Git needs a list of these. That list is a file named `.gitignore` at the
repo root. *Before reading on: which of the folders in lesson 00's tree
would you ignore?*

Create a new file at the repo root named `.gitignore` (note the leading
dot) with this content:

```gitignore
# --- Python ---
.venv/
__pycache__/
*.pyc
.pytest_cache/
.ruff_cache/

# --- Coverage reports (regenerated by tests) ---
.coverage
coverage.xml
htmlcov/
frontend/coverage/

# --- Database files (each dev makes their own) ---
*.db

# --- Node ---
node_modules/
dist/

# --- Secrets ---
.env

# --- OS clutter ---
.DS_Store
Thumbs.db
```

**Why ignore `*.db`?** Each developer creates their own database by
running migrations (lesson 04). Committing the file would overwrite
everyone's data with yours.

## Step 3 — `.gitattributes`

**Connect the dots.** Windows ends lines of text with two invisible
characters (`CRLF`); macOS and Linux use one (`LF`). Git hooks are shell
scripts, and a shell script with Windows line endings fails with
confusing errors like `\r: command not found`.

Create `.gitattributes` at the repo root:

```gitattributes
# Store and check out all text files with LF line endings.
* text=auto eol=lf
```

This tells Git to always use `LF`, on every machine. VS Code handles
`LF` files fine on Windows.

## Step 4 — Husky (Git hooks)

**What's a Git hook?** A script Git runs automatically at certain
moments. A **pre-commit** hook runs right before a commit is created. If
the script fails, **the commit is cancelled**.

**What's Husky?** A small tool that installs your hooks automatically
for anyone who clones the repo and runs `npm install`. Without Husky,
hooks live in `.git/hooks`, which Git never commits — so your teammates
wouldn't get them.

**The plan:** Husky needs a `package.json` at the repo root. You'll
create one just for this. Later, the pre-commit hook will run every
test in the project so broken code can't be committed.

From the repo root:

```bash
npm init -y
```

✅ Creates `package.json` at the root. `-y` means "accept all defaults".

```bash
npm install --save-dev husky
```

✅ Installs Husky and adds it under `"devDependencies"` in
`package.json`. A `node_modules/` folder and `package-lock.json` appear.

- **`--save-dev`** marks it as a *development* dependency: needed to
  build or test the project, not to run it.
- **`package-lock.json`** records the exact version of every installed
  package so everyone installs the same thing. Always commit it.

```bash
npx husky init
```

✅ This does two things:

1. Creates a `.husky/` folder containing a `pre-commit` file.
2. Adds `"prepare": "husky"` to the `"scripts"` in `package.json`.

**`npx`** runs a command from an installed package without you having to
find it. **`prepare`** is a special npm script that runs automatically
after `npm install` — that's how a classmate who clones your repo gets
the hooks installed without doing anything extra.

### Replace the default hook

Open `.husky/pre-commit`. Husky filled it with `npm test`, which would
fail right now (there are no tests yet). Replace the whole file with:

```sh
echo "Husky pre-commit hook ran."
```

For now, the hook only proves it runs. You'll add the backend tests to
it in lesson 03, the frontend tests in lesson 06, and linters in
lesson 08.

## Step 5 — VS Code workspace settings

**Connect the dots.** The Python extension needs to know where your
tests live. Coverage Gutters needs to know which report files to read.
Formatters need to know which language gets which tool. These settings
belong to *this project*, so they go in `.vscode/settings.json` and get
committed for everyone.

Create `.vscode/settings.json`:

```json
{
  "python.testing.pytestEnabled": true,
  "python.testing.cwd": "${workspaceFolder}/backend",
  "python.testing.pytestArgs": ["tests"],

  "coverage-gutters.coverageFileNames": [
    "lcov.info",
    "coverage.xml"
  ],
  "coverage-gutters.showLineCoverage": true,
  "coverage-gutters.showRulerCoverage": true,

  "editor.formatOnSave": true,
  "[python]": {
    "editor.defaultFormatter": "charliermarsh.ruff"
  },
  "[typescript]": {
    "editor.defaultFormatter": "esbenp.prettier-vscode"
  },
  "[typescriptreact]": {
    "editor.defaultFormatter": "esbenp.prettier-vscode"
  }
}
```

| Setting | What it does |
| --- | --- |
| `python.testing.*` | Tells the Python extension to use pytest, run from `backend/`, in the `tests` folder |
| `coverage-gutters.coverageFileNames` | The report files to look for: `lcov.info` (frontend) and `coverage.xml` (backend) |
| `showLineCoverage` / `showRulerCoverage` | Color the lines and the scrollbar |
| `editor.formatOnSave` | Formats files every time you save |
| `[python]`, `[typescript]`… | Which formatter to use per language |

> **Why not set the Python interpreter here?** Its path differs between
> Windows and macOS, so it can't be shared. You'll select it in lesson
> 03; VS Code remembers it just for you.

## Step 6 — First commit and push

```bash
git add .
git status
```

✅ `git status` lists the files *to be committed*. Check that
`node_modules/` is **not** in the list. If it is, your `.gitignore` has a
typo — fix it before continuing.

```bash
git commit -m "chore: scaffold repo with husky and editor settings"
```

✅ You should see `Husky pre-commit hook ran.` printed before the commit
summary. **That line is your proof the hook works.**

Now push to GitHub:

```bash
git branch -M main
git push -u origin main
```

- `git branch -M main` renames your branch to `main` (some Git installs
  default to `master`).
- `-u origin main` links your local `main` to GitHub's `main`, so future
  pushes are just `git push`.

### About commit messages

This guide uses a common style called **Conventional Commits**:
`type: short description`. Types you'll use:

| Type | For |
| --- | --- |
| `feat` | A new feature |
| `test` | Adding or changing tests only |
| `fix` | A bug fix |
| `chore` | Setup, config, tooling |
| `refactor` | Restructuring without changing behavior |
| `docs` | Documentation |

## Explain it back

**1. A classmate clones your repo and runs `npm install` at the root.
How do they end up with your pre-commit hook?**

<details>
<summary>Answer</summary>

`npm install` automatically runs the `prepare` script, which runs
`husky`, which installs the hooks from the committed `.husky/` folder.
</details>

**2. What happens to a commit if the pre-commit hook fails?**

<details>
<summary>Answer</summary>

The commit is cancelled. Nothing is committed until the hook passes.
</details>

**3. Why is `*.db` in `.gitignore`?**

<details>
<summary>Answer</summary>

Each developer builds their own database by running migrations.
Committing the file would share one person's local data with everyone
and cause conflicts.
</details>
